# ADR 0002: 파생값은 저장하지 않고 항상 계산한다

- **Date**: 2026-04-18
- **Status**: Accepted
- **Deciders**: 본인

## Context

paynote이 해결하려는 **가장 본질적인 문제**는 메모 방식의 합계 계산 오차다. 실측 예시 (2025-09 메모):

| 항목 | 메모 기재값 | 실제 합계 | 오차 |
|---|---|---|---|
| 총 수입 | 5,406,000 | 5,416,000 | +10,000 |
| 총 지출 | 3,083,000 | 3,163,000 | +80,000 |
| 잔액 | 2,590,000 | 2,253,000 | **-337,000** |

만약 DB에 `totalIncome`, `totalExpense`, `netBalance` 같은 컬럼을 두고 저장한다면:

- 항목이 추가·수정·삭제될 때마다 이 컬럼을 동기화해야 함.
- 업데이트 누락이 발생하면 메모 방식과 **정확히 같은 종류의 오차**가 DB 안에서 재발.
- 통장별 잔액(`accountDelta`), 이체 계획(`TransferPlan`) 같은 더 복잡한 파생값까지 저장하면 동기화 지점이 폭발적으로 늘어남.

## Decision

다음 값들은 **컬럼으로 저장하지 않고 항상 계산**한다:

- `totalIncome`, `totalExpense`, `netBalance`
- `accountDelta` (통장별 월간 순변동)
- `projectedAccountBalance` (월초 잔액 + accountDelta)
- `TransferPlan` (월말 이체 권장안)

저장하는 것은 **원자적 사실(atomic facts)**만이다:

- 개별 `IncomeItem` (금액, 라벨, 입금 통장)
- 개별 `ExpenseItem` (금액, 라벨, 출금 통장)
- `Account`의 시작 잔액 스냅샷 (신규 통장 추가 시 1회)

## Alternatives considered

- **파생값을 materialized view/캐시 컬럼으로 두고 트리거로 동기화**: SQLite에서 trigger 유지 복잡도. 단일 사용자 규모에서 성능 이득 없음.
- **앱 계층에서 저장하되 재계산 버튼 제공**: 사용자가 누르는 걸 잊으면 곧 오차 재발. 해결하려는 문제를 그대로 복제.
- **전부 계산하지만 일부만 저장 (예: 월 합계만)**: 경계가 임의적이라 규칙이 흐려짐. 나중에 어느 것이 파생이고 어느 것이 사실인지 판단하기 어려워짐.

## Consequences

### 얻은 것

- **정합성 보장**: 저장된 사실에서 항상 같은 결과가 나옴. 동기화 누락 오차 원천 차단.
- 스키마가 단순해짐 — 테이블 수 감소, 관계 복잡도 감소.
- 비즈니스 로직이 `src/domain/` 순수 함수에 모임 → 단위 테스트 용이.

### 포기한 것

- 매 조회마다 합계 재계산. (단일 사용자·수십 항목 규모라 실측 무시 가능.)
- 월별 통계를 SQL 집계 한 방으로 못 끝냄 — 앱 레이어 계산이 섞임.

### 유지 비용

- 새 파생값이 생길 때마다 **"이건 사실인가 계산인가"** 판단을 원칙대로 해야 함.
- PR 리뷰 시 "왜 저장했나?" 질문이 꾸준히 나와야 함.
